## When to Use This Skill

Load this skill when the user wants to **query a Context Engine AI Index** — i.e. to
retrieve Knowledge Indicators (KIs) that have already been generated.

This is the query-time complement to `analyze-and-improve`, which decides what the index should
contain and produces the automations that populate it.
This skill is not about generating these KIs, that is a separate skill.

## Tools

AI Indices have three dedicated tools. Use them in this order, and use nothing else to read an
AI Index:

1. **`list_ai_indices`** — the AI Indices you can use. Each entry has
   an `id`, the `esql_target` to put in `FROM`, and a description. An AI Index is left out when
   you cannot read its backing index; an empty AI Index is still listed. Skip this when your
   instructions already name the index.
2. **`describe_ai_index`** — takes an `id` and returns a context block you can read and copy
   ES|QL from: what the index holds, its fields and which are semantic, KI type and tag counts,
   and example queries. Fields differ between AI Indices, so describe one before filtering on a
   field.
3. **`query_ai_indices`** — runs your ES|QL and returns the rows. The server applies a row limit.

Do not use `execute_esql` or `list_indices` on AI Indices: only `list_ai_indices` knows which
`ai-index-*` indices are registered AI Indices, and `query_ai_indices` is the tool for reading them.

## What a KI index looks like

KIs are stored in indices matching `ai-index-*` (covers both regular indices and datastreams).
`list_ai_indices` tells you which of them are available to you and what to put in `FROM`.

### Field reference

| Field | ES\|QL type | Purpose |
|---|---|---|
| `type` | keyword | Categorization — e.g. `"index_metadata"`, `"document"`, `"entity_profile"` |
| `title` | text | Short name of the KI or its backing entity; semantic via `title.semantic` |
| `content` | text | Full text: purpose, questions answered, access patterns; semantic via `content.semantic` |
| `description` | text | Short description of this KI; semantic via `description.semantic` |
| `tags` | keyword | Filter facets |
| `attributes` | flattened | Structured keyword-queryable metadata (status, themes, entity names, etc.). `attributes.esql` is the canonical location for a KI's runnable ES\|QL — see below. |

Semantic sub-fields use **dot notation**: `content.semantic`, `title.semantic`, `description.semantic`.
The context block from `describe_ai_index` lists the fields an index actually has.

### `attributes.esql` — a KI's runnable ES|QL

When a KI carries runnable ES|QL (e.g. a `detection` KI's materialized query, or an
`index_metadata` KI's runnable example queries), those queries live in `attributes.esql`, as a
string or an array of strings. This is the canonical location — do not hunt for runnable
queries elsewhere in `attributes`. The prose access-pattern presentation (templates, params,
returns) also appears inside `content`.

The field is **optional**: only KI kinds that carry ES|QL set it, so queries must tolerate its
absence rather than assume every KI has it. `attributes` is `flattened`, so extract the value
with `FIELD_EXTRACT` before filtering or keeping it:

```esql
FROM <esql_target>
| WHERE type == "detection"
| EVAL esql = FIELD_EXTRACT(attributes, "esql")
| WHERE esql IS NOT NULL
| KEEP title, description, esql
| LIMIT <n>
```

When the KI stores an array of queries, the extracted value is multivalued: `IS NOT NULL`
still filters correctly, but scalar comparisons like `==` skip multivalued rows. Add
`| MV_EXPAND esql` after the `WHERE esql IS NOT NULL` to get one row per query when you
need per-query filtering.
